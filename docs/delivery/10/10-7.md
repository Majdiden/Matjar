## Requirements

1. Precedence: merchant override → brand-kit value (only when the brand value is non-empty) → manifest default.
2. Bilingual brand texts make an untouched Arabic store show Arabic.
3. Brand colour becomes the primary colour unless the merchant changed the theme's primary colour.
4. Storefront and dashboard live preview show the same effective values.
5. `GET /api/theme-customization` exposes, per setting, whether its value is an override, a brand value or a default.
6. A store with no brand data and no overrides renders exactly as before on every theme.

## The rule

For a setting with `bind`, given the stored values merged over the manifest defaults:

1. **Override** — the base key `<id>` holds something other than the manifest default, or the Arabic twin `<id>__ar` holds a non-blank value other than its default. Blank equals a blank default, so `""` stored for a setting whose default is `""` (or absent) is not an override; clearing a non-empty default is.
2. **Brand** — else, when the brand value is set (`store.name` / `store.logo` non-blank; brand texts need their Arabic text, which the brand-kit API always requires), the binding fills the setting.
3. **Default** — else the manifest default.

"Manifest default" for a section instance = the setting's `default` overlaid with the settings of the manifest template instance with the same id (`templates` + `homeVariants`) — the same merge ThemeProvider has always rendered.

**Bilingual rule.** Text settings are stored as a base key plus an optional `<id>__ar` twin (dashboard `SettingControl`); the storefront shows the twin when browsing in Arabic and the base key otherwise (`ThemeProvider` → `resolveI18nSettings`). A bilingual brand text `{ ar, en? }` therefore fills:

- `<id>` ← `en`, or `ar` when there is no English
- `<id>__ar` ← `ar`

Arabic visitors read Arabic, English visitors read English — or Arabic when none was given (the PRD's "missing English falls back to Arabic"). The store language plays no part, so an untouched Arabic store shows Arabic whichever language the visitor's browser starts in. Theme-level text settings now honour the twin too: `useThemeSetting(key)` returns `<key>__<lang>` when it is non-blank (it used to ignore twins for theme-level settings).

**Brand colour.** `primary` = the merchant's stored primary when it differs from the manifest colour (case-insensitive); else `brand.color` when set; else unchanged. The light palette only — a theme's `colorsDark.primary`, if any, still wins in dark mode.

## Where resolution happens

**In the storefront**, in `@matjar/theme-shared` `ThemeProvider` (`merged` settings and the CSS colour variables), using the pure functions in `theme/brandBindings.ts` and the store's `name`, `logo` and `brand` from the store payload. Reasons:

- The editor preview applies live edits by `postMessage` (`SECTION_UPDATE`, `SETTINGS_UPDATE`, …) straight into ThemeProvider, never through the server. Resolving server-side would show the default on the first live edit of a section and the brand value after a reload.
- It also covers the theme preview (`?previewTheme=`, where the server sends no customization) and stores without a published snapshot.
- The stored draft and published settings stay the merchant's own values. Brand values are never copied into the customization, so changing the brand kit later updates every page at once, and saving a section in the editor does not freeze today's brand values into overrides.

**In the backend**, `utils/themeBindings.js` mirrors the same rule (kept identical by `tests/unit/themeBindingsParity.test.js`, which runs both over the same cases) to annotate the dashboard payload.

`services/storefrontStoreInfo.js` is unchanged: it already sends `name`, `logo` and the public `brand`.

## API: `GET /api/theme-customization`

Read-time additions to `data.customization` (nothing is stored; `PUT /sections` strips them if an editor sends the payload back):

```jsonc
{
  // every section instance in `sections` and in each `sectionsByTemplate[tpl]` list:
  "settingSources": { "heading": "default", "subheading": "brand", "background_image": "override" },
  "brandValues": { "subheading": "Genuine perfumes", "subheading__ar": "عطور أصلية" },

  // top level:
  "settingSources": {
    "theme":  { "<theme setting id>": "override" | "brand" | "default" },
    "colors": { "primary": "brand", "secondary": "default" /* every manifest colour key */ }
  },
  "brandValues": {
    "theme":  { /* brand-filled theme-level keys, incl. __ar twins */ },
    "colors": { "primary": "#aa33cc" } // only when the brand colour applies
  }
}
```

- `settingSources` has one entry per setting declared by the section (or theme), keyed by base id; values are `SETTING_SOURCES` (`'override' | 'brand' | 'default'`).
- `brandValues` holds exactly the keys the storefront fills from the brand kit, including `<id>__ar` twins. Effective value for the editor = `brandValues[key]` when the source is `brand`, else `settings[key]`.
- `settings` remain the stored draft values. To hand a setting back to the brand kit, remove its key (or write the manifest default) and remove its `__ar` twin.
- Annotations are computed on the active theme's manifest. A section whose type is unknown carries none.

## Implementation Plan

- `_shared/theme/brandBindings.ts`: `brandBindingValue`, `brandSettingValues`, `isSettingOverridden`, `resolveBoundSettings(defs, values, defaults, source)` → `{ settings, sources, brandValues }` (returns the same `values` object when nothing is filled), `resolvePrimaryColor(manifestColor, storedColor, source)` → `{ color, source }`.
- `_shared/theme/ThemeProvider.tsx`: `brandSource` from the store; `lightPalette` (used by `merged.colors` and the CSS variables) applies the brand colour only when its source is `brand`; theme-level settings and every section with a bound setting go through `resolveBoundSettings`; `useThemeSetting` honours `__<lang>` twins.
- `utils/themeBindings.js`: backend mirror + `brandBindingSourceFor(tenant, publicBrand)` + `manifestInstanceDefaults(manifest)`.
- `services/themeCustomization.js`: annotations in `getThemeCustomizationService`; `updateThemeSectionsService` drops them on write. `repositories/themeCustomization.js` also selects the tenant `name` (store-name fallback).
