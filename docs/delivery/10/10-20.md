# [10-20] Automatic product/category links from Arabic names

[Back to task list](./tasks.md)

## Description

Merchants (mostly Arabic speakers, low tech literacy) should never have to invent a URL slug. The server already derived a product slug from the name when none was sent, but every backend slugify dropped non-Latin characters, so an Arabic name such as "عطر الورد" gave an empty or fallback slug, and the dashboard's product form required a "Slug *" field that an Arabic name left empty.

This task makes one backend slug implementation that transliterates Arabic exactly like the dashboard's store-link helper (PBI 10-1), uses it for products, categories, collections, pages, menus, markets and seed data, keeps shared links stable when a product is renamed, and replaces the product/category slug inputs with a read-only link preview.

## Requirements

1. One backend slug implementation (`utils/slugify.js`) with the same Arabic → Latin mapping as `dashboard/src/lib/storeLink.ts` (Sudanese everyday spelling, و/ي consonant at word start and vowel inside, Arabic-Indic digits, diacritics/tatweel and invisible format characters stripped). A parity test fails if the two drift.
2. `slugify(input, { maxLength = 100 })` never leaves a leading/trailing hyphen; `ensureUniqueSlug(exists, base, { fallback })` suffixes `-2`, `-3`, … with bounded attempts, and an empty base becomes `<fallback>-<6 hex>`, so a slug always exists.
3. Products and categories: no slug sent → derived from the English name if present, else the primary (often Arabic) name; a sent slug is normalised with the same rule (free text accepted, no 400 for spaces/Arabic).
4. Renaming a product or category never changes its slug. Only an explicit slug edit does; for a published item (status `active`) the old storefront URL (`/products/<old>`, `/categories/<old>`) then 301-redirects to the new one through the Redirect service. Changing again repoints older redirects (no chains); changing back removes the redirect away from the restored URL.
5. Collections: same rules for `handle` (title change keeps it; an explicit handle change on a published collection redirects `/collections/<old>`).
6. Dashboard product form and category dialog: the link is shown read-only ("رابط المنتج" / "Product link": `https://<store>/products/<slug>`), following the name for new items; the slug input sits behind "تعديل الرابط" / "Edit link". The slug is sent only when edited. Arabic copy is plain, natural standard Arabic.

## Implementation Plan

- `utils/slugify.js` (new): `cleanInput`, `transliterateArabic`, `slugify`, `randomSlug`, `ensureUniqueSlug`.
- `dashboard/src/lib/storeLink.ts`: `slugifyLink(name, maxLength = 100)` (preview twin of `slugify`), "keep in sync" pointers both ways.
- Services: `product.js` (create derive/normalise/dedupe; update normalises an explicit slug, 409 on conflict, redirect when published), `category.js` (same; also fixes update/delete that filtered by the always-undefined `req.path.id` and so hit the tenant's first category), `collection.js` (bounded `uniqueHandle`, redirect on published handle change), `page.js` (default slug from title via `slugify`; explicit slugs stay strictly validated), `menu.js`, `dataSeed.js`, `controllers/market.js` (same intent, swapped to the shared helper).
- `services/redirect.js` `redirectRenamedPath(models, oldPath, newPath)` + repository helpers `deleteRedirectByFromPathRepo`, `retargetRedirectsRepo`.
- `validators/product.validator.js`: slug accepts free text (≤ 200 chars); the service normalises to `[a-z0-9-]`.
- Dashboard: `components/LinkSlugField.tsx` (new), `hooks/useStorefrontHost.ts` (new), `ProductForm.tsx`, `Categories.tsx`, `CategoryPicker.tsx` (no client-side slug), `PageForm.tsx` / `CollectionForm.tsx` previews use `slugifyLink`, `types` (`Category.status`), i18n `products.form.field.slug.*`, `products.categories.form.field.slug.*` (en + ar).
