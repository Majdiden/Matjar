# [10-6] Manifest `level` / `bind` / niche presets

[Back to task list](./tasks.md)

## Description

Extend the theme manifest contract so a theme can say which settings the phone-first simple editor shows (`level`), which settings take their value from the brand kit when the merchant has not changed them (`bind`), and which homepage a new store of a given niche starts from (`presets`). Validate all three at theme build time and in the backend. Stores without brand data render exactly as before.

## Requirements

1. `SettingDefinition.level?: 'basic' | 'advanced'` — absent means `advanced`. `SectionDefinition.level?: 'basic' | 'advanced'` — absent means `basic` (listed in simple mode; only its basic settings are editable there). At most 3 basic settings per section.
2. `SettingDefinition.bind?: BrandBinding`, `BrandBinding = 'store.name' | 'store.logo' | 'brand.tagline' | 'brand.coverImage' | 'brand.color' | 'brand.whatsapp' | 'brand.city' | 'brand.hours'`. Allowed on section and theme-level settings (not block settings), only on compatible setting types.
3. `ThemeManifest.presets?: Partial<Record<NicheId, { index: SectionInstance[] }>>`, `NicheId` = the signup niches (`fashion`, `electronics`, `food`, `sports`, `books`, `toys`, `home`, `general`).
4. A new store uses `presets[niche].index` instead of `templates.index` when its theme ships one; existing stores and theme switches are unchanged.
5. `services/themeValidator.js` and the theme package linter accept and check `level` / `bind` / `presets`.

## Contract (as implemented)

Types live in `storefront-themes/_shared/types/theme.ts` and are exported from `@matjar/theme-shared`: `SettingLevel`, `BrandBinding`, `NicheId`, `SettingSource` (`'override' | 'brand' | 'default'`), `ThemeNichePreset`. `level` and `bind` are on `SectionSettingBase` (so on every setting type) and on the loose `AnySectionSetting` the dashboard uses; `level` is on `SectionDefinition`; `presets` is on `ThemeManifest`.

Helpers, `storefront-themes/_shared/theme/settingLevels.ts` (also exported from the package index):

- `SETTING_LEVELS = ['basic', 'advanced']`, `DEFAULT_SETTING_LEVEL = 'advanced'`, `DEFAULT_SECTION_LEVEL = 'basic'`, `MAX_BASIC_SETTINGS_PER_SECTION = 3`
- `isBasicSetting(setting)` → `setting.level === 'basic'`
- `isBasicSection(section)` → `(section.level ?? 'basic') === 'basic'`
- `basicSettingsOf(section)` → the section's basic settings in manifest order

Binding constants, `storefront-themes/_shared/theme/brandBindings.ts` (exported): `BRAND_BINDINGS`, `BILINGUAL_BRAND_BINDINGS` (`brand.tagline`, `brand.city`, `brand.hours`), `BRAND_BINDING_SETTING_TYPES`, `SETTING_SOURCES`, `NICHE_IDS`, `ARABIC_SETTING_SUFFIX = '__ar'`, `BRAND_COLOR_TOKEN = 'primary'`. The resolution rule is in [10-7](./10-7.md).

Allowed setting types per binding (rich text is excluded on purpose — brand texts are plain text and must never be rendered as HTML):

| Binding | Setting types |
|---|---|
| `store.name` | text |
| `store.logo` | image |
| `brand.tagline`, `brand.city`, `brand.hours` | text, textarea |
| `brand.coverImage` | image |
| `brand.color` | color |
| `brand.whatsapp` | text |

Preset rules (validator): keys are signup niches; `index` is an array of section instances with unique ids, declared types, valid settings and section limits respected; it holds every id of `templates.index` (reorder, or hide with `disabled: true` — the editor re-adds a manifest index section missing from a store's list, so dropping one would not stick); it never sets a bound setting or its `__ar` twin (a preset value would count as the merchant's own and hide their brand kit).

Preset selection: `services/theme.js` → `selectIndexTemplate(manifest, niche)` returns `presets[niche].index` when present and non-empty, else `templates.index`. `buildCustomizationFromManifest(slug, { niche })` uses it for the `index` bucket only. `installDefaultTheme(tenant)` (store setup) passes `tenant.settings.niche` when `design.simpleMode` is on for the store, else no niche. The theme-switch path passes no niche.

Niche storage: the signup niche was sent by the dashboard but never stored. `tenant.settings.niche` (String, default null) is now written at registration from `config/storeNiches.js` → `normalizeStoreNiche` (known niche or null). Existing stores keep null.

## Implementation Plan

- `_shared/types/theme.ts`: the types above; `_shared/theme/settingLevels.ts`, `_shared/theme/brandBindings.ts`; exports in `_shared/index.ts`.
- `utils/themeManifestRules.js` → `validateManifestExtensions(manifest)` (dependency-free, shared); `services/themeValidator.js` → `validateThemeManifest(slugOrManifest)`; `scripts/validate-theme.js` runs it after every theme build (a bad annotation fails the build).
- `utils/themeBindings.js` (backend mirror of the binding constants), `config/storeNiches.js` (`STORE_NICHES`, `normalizeStoreNiche`).
- `schemas/tenant.js` `settings.niche`; `services/tenant.js` stores it.
- `services/theme.js`: `selectIndexTemplate`, `buildCustomizationFromManifest(slug, { niche })`, flag-gated use in `installDefaultTheme`; `config/featureFlags.js` flag description mentions it.
- `modern` ships two presets (`food`, `books`): same sections, reordered, photo slider hidden. The shared section instances moved into a `HOME` constant so the template and presets cannot drift; `templates.index` is byte-identical in the built manifest.
