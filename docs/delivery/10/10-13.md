# [10-13] Homepage simple editor

[Back to task list](./tasks.md)

## Description

The phone-first homepage editor at `/dashboard/store/homepage` ("الصفحة الرئيسية" in the "متجري" hub), behind `design.simpleMode` and the `themes.write` permission. It replaces the 10-12 placeholder. The merchant sees a phone-sized preview of their homepage and, under it, the homepage's parts in plain words; each part can be shown or hidden, moved up or down, and tapped to change its few basic settings in a bottom sheet. There is no draft: every change is saved and goes live at once, with Undo. The full theme editor stays one tap away as "Advanced options".

## Requirements

1. Route `/dashboard/store/homepage`, behind `design.simpleMode` + `themes.write`; the placeholder file, route and `homepage_placeholder.*` strings are gone.
2. Phone preview of the homepage that follows each change live, using the full editor's postMessage protocol (`SECTION_UPDATE`, `SECTION_TOGGLE`, `SECTION_REORDER`, `SCROLL_TO_SECTION`).
3. A list of the homepage's sections in plain words — only sections where `isBasicSection` is true (and whose type the active theme still declares). Each row: name, show/hide switch, move up / move down buttons, tap to edit.
4. Tap → bottom sheet with ONLY `basicSettingsOf(section)` controls: text/textarea via `BilingualField` (Arabic first, English optional), image via the existing photo upload (`ImageField`, shrunk on the phone), colour swatches (`ColorField`), checkbox as a switch, select as large options, number/range as a number box.
5. A setting whose source is `brand` shows the brand value, "From your store info" and a link to `/dashboard/store/brand`; editing it makes an override; an overridden bound setting offers "Use my store info again", which removes the override.
6. No draft/publish for the merchant: each change is saved and published at once, then shows "Saved — live on your store" with Undo.
7. No lost input on a dropped connection: changes are kept on the phone until the server has them and are retried (useStoreProfile's pattern).
8. Hub card status: "N of M parts shown to customers".
9. "Advanced options" links to the full editor.
10. Works at 360–430px in RTL and LTR with no horizontal scroll; big tap targets; no design vocabulary; Arabic copy per the PRD copy guideline; strings in `storeDesign.json` (en + ar).

## Design decisions

### Saving = save + publish

Each change calls the existing endpoint for it — `PATCH /theme-customization/sections/:id/settings`, `POST /sections/:id/toggle` or `POST /sections/reorder` (all `?template=index`) — and then `POST /theme-customization/publish`, the same call the full editor's Publish button makes (it validates the draft, records a version row and copies the draft to the live snapshot). No backend changes were needed.

`hooks/useHomepageEditor.ts` keeps one queue of waiting changes, newest per key (`settings:<id>`, `visible:<id>`, `order`), stored in localStorage (`matjar.homepageEdits.v1:<store>`) **before** anything is sent and removed only after the server accepted it. Changes go out one at a time, in order; once nothing is waiting, one publish follows. Network failures, 5xx and 429 retry with 3/6/12/24/30 s backoff and on `online` (the same `RETRY_DELAYS_S` / `isRetryableError` as `useProfileAutosave`); the bar shows "Not saved yet — we'll try again" with "Try now". On the next visit, waiting changes are applied on top of what loads and sent again (dropped if their section no longer exists, or if the store switched to another look). The last loaded homepage is cached per store too, so the screen opens offline. A refused change (4xx, or a publish the validator rejects) is dropped and the page reloads what the store really has, with a plain message.

Publish publishes the whole draft. If the full editor has unpublished work (`isDraft`), the page says so in a notice ("…will show together with your next change here") before the first change.

### Undo: re-apply the previous value (not version rollback)

Before each change, the editor records its inverse — the section's previous settings (with their sources), its previous visibility, or the previous order — and Undo sends that through the same queue, followed by a publish. Up to 20 steps are kept in memory.

Why not `POST /versions/:n/rollback`:

- Rollback restores the **whole** look (all templates, colours, custom CSS) to the snapshot, so it would also throw away anything else changed in between (another staff member, the full editor, a second tab). The inverse change only touches what this change touched.
- Rollback only restores the draft; it needs a second publish anyway, and writes a "rollback" version row plus a publish row for one tap.
- A store whose first publish is a simple-editor change may have no earlier version row to roll back to.
- The inverse change goes through the same offline-safe queue, so an Undo made on a weak connection is never lost either. Every Undo is still recorded as a normal published version.

### Bilingual mapping

Text settings are stored as a base key plus an Arabic twin `<id>__ar` (the full editor's `SettingControl` convention; the storefront shows the twin to Arabic visitors and the base key to everyone else). The simple editor maps one Arabic-first `BilingualField` onto them exactly like a bilingual brand-kit text is mapped in 10-7 (`lib/homepageEditor.ts` → `writeBilingual` / `readBilingual`):

| BilingualField | stored |
|---|---|
| `{ ar, en }` | `<id>__ar` = ar, `<id>` = en |
| `{ ar }` (no English) | `<id>__ar` = ar, `<id>` = ar (English visitors see Arabic — the PRD fallback) |
| both empty | `<id>` = "", `<id>__ar` removed |

Reading back: ar ← `<id>__ar`; en ← `<id>` when it differs from the twin. A base value with no twin (typed in the full editor) shows as Arabic if it contains Arabic letters, else as English. A unit test checks that `writeBilingual` produces exactly the keys `brandSettingValues` fills for the same `{ ar, en? }`.

### Where a value comes from

The sheet shows `brandValues[key]` when `settingSources[id]` is `brand`, else `settings[key]` (from `GET /theme-customization`). Editing writes the merchant's value (source → `override`). "Use my store info again" removes the key and its `__ar` twin from the stored settings (`withoutOverride`), so the brand kit fills it again. The brand value shown after that comes from the server annotation or, when the setting was overridden at load, from the store profile through the shared `brandSettingValues`. Sources are updated on screen right away and refreshed from the server after each publish. Clearing a bound text whose default is blank also hands it back to the brand kit (blank is not an override, per 10-7).

The live preview merges `SECTION_UPDATE` settings over what it has, so removed keys are sent as their default (theme default for the base key, blank for the twin) — `liveSettings`.

### Layout

Phones: preview (36% of the screen height, the page scrolls inside it; "Hide" remembered per phone) above the list. The sheet is the dashboard's Dialog (a bottom sheet on phones) opened **non-modal** with at most 60% of the screen height, so the preview above it stays visible and undimmed and scrolls to the part being edited; its footer keeps the save state, Undo and "Done" in view. The page's own save bar sticks above the bottom navigation. Desktop: list beside a full phone preview; the sheet is a centred panel.

### Moving

Up/down swaps a part with its neighbour among the listed parts only; sections the simple editor doesn't list (advanced level, unknown type) keep their positions (`moveAmong`). The reorder API drops sections missing from the id list, so the full id list is always sent, and a saved order is reconciled with the current list before replay (`reconcileOrder`).

### Plain names

Part names: `storeDesign:homepage.parts.<type>` (e.g. hero → "Big photo at the top" / "الصورة الكبيرة في أعلى الصفحة"), falling back to `themes:sections.<type>.name`, then the manifest name. Field names: `storeDesign:homepage.fields.<id>`, then `themes:settings.<id>.label`, then the manifest label.
