# [10-15] Theme switch keeps brand kit and content

[Back to task list](./tasks.md)

## Description

Verify that switching the active theme keeps the brand kit and the merchant's content, and that one theme's customization is neither lost nor applied to another theme; fix what does not hold.

## Requirements

1. The brand kit (`tenant.settings.brand`, store name, logo, social links) survives any theme switch and feeds the new theme.
2. Each theme's customization (sections, settings, colours, custom CSS) is never applied to another theme.
3. A theme the merchant used before comes back as they left it, instead of being reset to its defaults.

## Findings (before the change)

- Brand kit: kept. It lives on `tenant.settings`, which `installThemeService` does not touch, and the storefront payload reads it independently of the theme. Products, categories, pages and menus are not touched either.
- Cross-application: none. The switch overwrote the draft and published customization with the new theme's manifest defaults and cleared custom CSS and the preview token.
- Loss: yes. That overwrite discarded the outgoing theme's customization, so switching A → B → A brought A back with its defaults and every edit (texts, images, section order, colours, custom CSS) gone.

## Fix

`services/theme.js` → `installThemeService`:

- Before switching away, the outgoing theme's draft and published customization are kept under `themeCustomization.savedByTheme.<slug>` (`{ savedAt, isDraft, draft: { settings, sectionsByTemplate, customCSS }, published | null }`; the published part only when it belongs to that theme).
- When switching to a theme with a saved entry, each part is restored only if it still validates against the theme's current manifest (`validateCustomization`) and CSS policy (`validateCustomCSS`); a part that no longer validates falls back to the manifest defaults (a missing draft falls back to the restored published part). The draft flag comes back with the draft. The entry for the incoming theme is then removed.
- A theme with no saved entry (first use) gets the manifest defaults exactly as before. The audit row (`theme_switch`) records what is now live.
- `schemas/tenant.js` declares `savedByTheme` (Mixed). `GET /api/theme-customization` removes it from the payload; the storefront payload never included it.

## Test Plan

E2E `tests/e2e/theme-brand-bindings.test.js` ("switching theme keeps the brand kit and each theme's own customization"), through `POST /api/themes/:id/install`:

1. Store on `modern` with a brand kit; modern customized (hero subheading, primary colour, custom CSS) and published.
2. Switch to `starter`: brand kit unchanged (`GET /api/store-profile`), storefront payload has theme `starter` + brand colour, the starter hero's subheading is sourced from the brand kit, no modern text / colour / CSS present.
3. Edit starter (unpublished), switch back to `modern`: modern's subheading (`override`), colour and CSS are back, live on the storefront payload; starter's edit is absent.
4. Switch to `starter` again: its unpublished edit is back, still a draft. Only the theme not in use is kept aside.
