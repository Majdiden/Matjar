# [10-16] Signup reorder (onboarding v2)

[Back to task list](./tasks.md)

## Description

A new signup order for first-time merchants, one question per screen: who you are → what your store is called → what you sell → where you are and where you deliver → pick a look. The answers fill the brand kit at creation, so a new store starts with a WhatsApp number, a city and delivery areas instead of empty fields. Ships behind the global `onboarding.v2` flag; v1 is unchanged when it is off.

## Requirements

1. New flag `onboarding.v2` (boolean, default off, group Onboarding) in `config/featureFlags.js`, mirrored in `dashboard/src/lib/features.ts`.
2. Signup runs before a store exists, so the register page reads the **global** value from a public endpoint `GET /api/auth/onboarding-config` → `{ v2 }`. The URL overrides `?flow=v2` / `?flow=v1` win over the flag so the operator can try v2 on prod while it is off. If the config can't be loaded, v1 runs.
3. v2 order: welcome → account (name, email, phone, password; email OTP unchanged, so security is the same) → OTP → store name (+ the automatic link from 10-1, unchanged) → what you sell (niche cards) → **where are you / where do you deliver** → pick a look.
4. Location step: city (required, 2–80 characters) → brand kit `settings.brand.city.ar`; delivery areas (optional free text, up to 300 characters, line breaks become commas) → `settings.policyAnswers.deliveryAreas.ar`, for 10-11 to reuse.
5. Look step: at most 3 themes, the niche's own themes first, each card showing the merchant's store name over the screenshot.
6. The store's WhatsApp (`settings.brand.whatsapp`) defaults to the account phone, server side, only for v2 signups and only when the phone is valid. The phone has already been normalised to E.164 by the signup, so it is a valid WhatsApp number. Add-store in v2 does the same with the account's phone.
7. v2 stores are marked `tenant.onboarding.flow = "v2"` (used for 10-18 metrics). v1 signups write nothing new: the v2 fields are ignored without `onboardingFlow: "v2"`.
8. All new data is additive, optional and has no defaults. Bad v2 input is a 400, with nothing written.

## Implementation Plan

- `config/featureFlags.js`: register `onboarding.v2`; `dashboard/src/lib/features.ts` mirror.
- `controllers/auth.js` `onboardingConfigController` + `routes/auth.js` `GET /auth/onboarding-config` (public, cached 60s).
- `validators/auth.validator.js`: optional `onboardingFlow` (`v1|v2`), `city`, `deliveryAreas`.
- `services/tenant.js`: `buildSignupV2Settings()` validates before any write and returns the brand/policy-answer settings; it is wired into the tenant payload. Add-store passes the same fields (`controllers/auth.js`).
- `utils/policyAnswers.js` (new): `DELIVERY_AREAS_MAX_LENGTH`, `normalizeDeliveryAreas`.
- `schemas/tenant.js`: `settings.policyAnswers.deliveryAreas { ar, en }`, `onboarding { flow, sharedAt, paymentsReviewedAt }` (no defaults).
- `dashboard/src/lib/onboarding.ts` (new, pure): `resolveSignupFlow`, `signupSteps`, `themesForNiche`, `SIGNUP_V2_THEME_LIMIT`.
- `dashboard/src/pages/Register.tsx`: flow resolution (locked on the first step change so a late config response can't reshuffle steps), location step, v2 headings, 3 theme cards with the store name, v2 fields sent on register and add-store.
- i18n: new namespace `onboarding` (`dashboard/src/i18n/locales/{en,ar}/onboarding.json`, registered in `resources.ts`); v1 strings in `auth.json` untouched.
